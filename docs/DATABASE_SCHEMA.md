# Running Coach App — Database Schema

PostgreSQL schema for the MVP. Designed so every backlog item in
`SUGGESTIONS_LOG.md` is an additive change (new tables, new columns), not
a restructure of what's here.

## Design principles

1. **Normalize the relational stuff, JSON the flexible stuff.** User identity,
   billing, and run-to-user relationships are relational. Strava's raw activity
   payload, the structured debrief output, and memory entries are JSON columns
   so the shape can evolve without migrations.
2. **Soft-delete, don't hard-delete.** Add `deleted_at` to every user-facing
   table. Users will ask to undo deletions, and analytics depend on it.
3. **Timestamps on everything.** `created_at` and `updated_at` are mandatory.
   Auto-set via triggers.
4. **One source of truth per concept.** A run's pace lives in the `runs` table,
   not duplicated into `debriefs`. Debriefs reference runs.
5. **Tier and trial state live on the user, not in billing.** This way the app
   doesn't need to call Stripe on every request to know what to render.

The core identity record.

|---|---|---|

| `password_hash` | text, nullable | Null if user only uses Google OAuth. |
| `google_oauth_id` | text, nullable | |

### `goals`

A user's target race. One goal per user — upserted on every save via a unique
index on `user_id`. No historical goals kept in this table; past race context
lives in `user_memories` instead.

| Column | Type | Notes |
|---|---|---|
| `id` | serial (PK) | Auto-incrementing integer. |
| `user_id` | uuid (FK → users.id, NOT NULL) | |
| `race_name` | text | "Berlin Marathon" — optional. |
| `race_distance` | text | "Marathon", "Half Marathon", "5K", etc. Required for meaningful coaching. |
| `race_date` | date | Optional — used to compute weeks_until_race in the prompt. |
| `goal_time` | text | e.g. "3:59:59" — stored as plain text, not a Postgres interval. |
| `created_at` | timestamptz | DEFAULT now() |
| `updated_at` | timestamptz | DEFAULT now() |

**Indexes:** `goals_user_id_idx` (UNIQUE) — enforces one goal per user, enables fast upsert.

### `runs`

Every run logged for a user, regardless of source (Strava, manual, future
wearable). Source-agnostic columns at the top level, raw source payload in JSON.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid (PK) | |
| `user_id` | uuid (FK → users.id) | |
| `source` | enum('strava', 'manual', 'garmin', 'apple_health') | |
| `source_id` | text, nullable | Strava activity_id, etc. Null for manual. |
| `started_at` | timestamptz, not null | When the run started. |
| `run_type` | enum('easy', 'tempo', 'long', 'intervals', 'race', 'recovery', 'mp_run', 'unknown') | |
| `distance_meters` | float, not null | SI unit at storage. Convert in app layer. |
| `duration_seconds` | int, not null | |
| `avg_pace_seconds_per_km` | int, computed | Generated column from distance + duration. |
| `avg_heart_rate` | int, nullable | |
| `hr_zone_breakdown` | jsonb, nullable | `{"z1": 0.10, "z2": 0.55, ...}` |
| `splits` | jsonb, nullable | Array of per-mile or per-km objects. |
| `elevation_gain_meters` | float, nullable | |
| `notes` | text, nullable | User-entered free text about this specific run. |
| `raw_payload` | jsonb, nullable | Original Strava (or other) payload, untouched. |
| `created_at` | timestamptz | |
| `updated_at` | timestamptz | |
| `deleted_at` | timestamptz, nullable | |

**Indexes:** `user_id` + `started_at` desc (the most common query — "last N runs"), `source_id` (for webhook deduplication).

**Why store distance in meters and pace as seconds-per-km:** SI units at the storage layer, presentation layer handles miles/km conversion. No ambiguity bugs.

### `debriefs`

The generated coaching output. Stored so users can scroll back through history
and so we can analyze what's been generated for cost tracking and prompt regression
analysis.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid (PK) | |
| `run_id` | uuid (FK → runs.id, UNIQUE) | One debrief per run. Cached — never re-generated on page revisit. |
| `user_id` | uuid (FK → users.id) | Denormalized. |
| `tier_at_generation` | text CHECK ('trial', 'free', 'paid') | What tier the user was on when generated. |
| `prompt_version` | text, not null | e.g. "v4.2". For regression tracking. |
| `model` | text, not null | e.g. "claude-haiku-4-5-20251001". For cost analysis. |
| `content` | text, not null | Full debrief output — includes both THE DEBRIEF and THE WEEK AHEAD (paid) in one block. |
| `input_tokens` | int | For cost tracking. |
| `output_tokens` | int | |
| `status` | text | CHECK ('generating', 'complete', 'failed'). DEFAULT 'complete'. |
| `error_message` | text, nullable | Set when status = 'failed'. |
| `created_at` | timestamptz | |
| `updated_at` | timestamptz | |

**Indexes:** `debriefs_user_idx` on (`user_id`, `created_at` DESC), `debriefs_run_idx` on (`run_id`).

### `user_memories`

The S-009 persistent memory store. Each row is one key/value fact the coach has
extracted from a debrief. User can view and delete entries at `/dashboard/memories`.
Injected into the debrief prompt as `--- USER MEMORY ---` with temporal filtering
(only memories created before the run's `started_at` are included).

| Column | Type | Notes |
|---|---|---|
| `id` | uuid (PK) | DEFAULT gen_random_uuid() |
| `user_id` | uuid (FK → users.id, NOT NULL) | ON DELETE CASCADE |
| `key` | text, not null | Category label. e.g. "injury_history", "life_pattern". Used for DISTINCT ON deduplication. |
| `value` | text, not null | The fact itself. e.g. "Hamstrings flare up above 45mi/week." |
| `source` | text, not null | DEFAULT 'extraction'. Where it came from. |
| `run_id` | uuid (FK → runs.id), nullable | Which run triggered the extraction. ON DELETE SET NULL. |
| `created_at` | timestamptz, not null | DEFAULT now() |
| `updated_at` | timestamptz, not null | DEFAULT now() |

**Indexes:** `user_memories_user_idx` on (`user_id`), `user_memories_run_idx` on (`run_id`).

**Deduplication:** Injection query uses `DISTINCT ON (key) ORDER BY key, created_at DESC` — one entry per key type, newest wins. All rows remain visible to the user for review/deletion.

**Safety:** Extraction prompt explicitly excludes weight, medications, and clinical diagnoses. Training context only.

## Planned tables (not yet implemented)

The tables below are designed and ready to build. They are not in the database yet. Each maps to a specific step in Phase 1.

### `training_plans`

The S-010 plan ingestion. One active plan per user at a time, but historical
plans are kept.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid (PK) | |
| `user_id` | uuid (FK → users.id) | |
| `goal_id` | uuid (FK → goals.id) | Plan is tied to a specific goal. |
| `plan_name` | text | "Higdon Advanced 1," "My custom plan," etc. |
| `plan_source` | enum('pasted_text', 'parsed_pdf', 'template') | MVP only uses 'pasted_text'. |
| `raw_text` | text | What the user pasted, unmodified. |
| `parsed_structure` | jsonb | Normalized week-by-week structure. See format below. |
| `status` | enum('active', 'completed', 'replaced', 'abandoned') | |
| `created_at` | timestamptz | |
| `updated_at` | timestamptz | |

**`parsed_structure` JSON shape:**

```json
{
  "weeks": [
    {
      "week_number": 10,
      "start_date": "2026-05-11",
      "workouts": [
        { "day": "mon", "type": "rest", "description": "Rest day" },
        { "day": "tue", "type": "intervals", "description": "6x800m @ 5K pace, 90s recovery" },
        { "day": "wed", "type": "easy", "description": "5mi easy" },
        { "day": "thu", "type": "mp_run", "description": "7mi w/ 4mi @ MP" },
        { "day": "fri", "type": "rest", "description": "Rest" },
        { "day": "sat", "type": "easy", "description": "4mi easy" },
        { "day": "sun", "type": "long", "description": "18mi long run" }
      ]
    }
  ]
}
```

**For MVP:** Parsing is a single LLM call that takes the pasted text and
returns this structure. Stored once, read many times.

**Indexes:** `user_id` + `status` (for finding active plan).

### `plan_adaptations`

When the WEEK AHEAD adjusts the plan, record the change. This becomes the
audit trail and the data for B-007 (push adapted workout to watch) later.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid (PK) | |
| `plan_id` | uuid (FK → training_plans.id) | |
| `debrief_id` | uuid (FK → debriefs.id) | The debrief that produced this adaptation. |
| `target_date` | date | Which day's workout is being changed. |
| `original_workout` | jsonb | What the plan said. |
| `adapted_workout` | jsonb | What the coach recommends instead. |
| `reason` | text | Coach's stated reason. |
| `user_accepted` | boolean, nullable | Did the user follow the adaptation? Filled in retroactively when their run on `target_date` is logged. |
| `created_at` | timestamptz | |

**Why this table matters:** Without it, the WEEK AHEAD text is just a paragraph.
With it, you can later (a) push the adapted workout to the user's watch, (b)
track whether adaptations actually help (did acceptance correlate with better
runs?), (c) train a future model on which adaptations worked.

## How backlog items extend this schema

Validating the "no backtracking" claim — every backlog item is an addition:

| Backlog item | What changes |
|---|---|
| **B-001** Weekly summary | New table `weekly_summaries` with same shape as `debriefs`. |
| **B-002** Haiku for free | No schema change. `debriefs.model_used` already tracks. |
| **B-003** Wearable integration | New `wearable_connections` table. `run_contexts.source` enum gets new values (already future-proofed). |
| **B-007** Watch sync | New `synced_workouts` table with FK to `plan_adaptations`. |
| **B-008** Proactive check-ins | New `scheduled_check_ins` table. |
| **B-009** Hard-gate weekly check-in | New `weekly_check_ins` table. Optional FK from `debriefs` to gate generation. |
| **B-010** Conversational follow-up | New `conversations` and `messages` tables. `debriefs.id` becomes the conversation seed. |

No existing tables get restructured for any of these. That's the test.

## Migration strategy

Use a migration tool from day one. For Node: Prisma (also gives you an ORM)
or Kysely + a tool like `node-pg-migrate`. For Python: Alembic.

Two rules:
1. **Never edit a migration after it's run in any environment.** Always create
   a new one.
2. **All schema changes go through migrations, even in development.** Resist
   the urge to just `ALTER TABLE` in psql.

## What's NOT in this schema (and why)

- **No `runs.summary_text`** — debriefs ARE the summary. Don't duplicate.
- **No `users.timezone`** — store on `events` if needed; for now infer from
  Strava activity times.
- **No `friends`, `groups`, `social_feed`** — not a social product.
- **No `achievements`, `badges`** — anti-pattern for this audience. Marathon
  runners are intrinsically motivated.
- **No `notification_preferences`** table yet — single global toggle per user
  is fine for MVP, add granular preferences in v2 if needed.
